## 1. Proposed architecture

- **Verified baseline:** `/home/runner/work/az-monitor-alert/az-monitor-alert/README.md` contains only the repository title. No Go entry point, execution boundary, logging/telemetry, Azure infrastructure, build commands, or tests exist in this checkout. The application and deployed configuration must be supplied before implementation.
- **Selected approach:** Go execution events as structured JSON on stdout/stderr → Azure Container Apps environment logging → Log Analytics → Azure Monitor scheduled query rules → action group email notifications. No notification service or application-side alert-management API is needed: the application emits signals; Azure Monitor evaluates conditions and fires alerts.
- At the actual work boundary, emit `started` and one terminal `succeeded` or `failed` event, with UTC event time, logical execution ID, unique attempt ID, workload name, duration, and a sanitized error summary. Success means completed business work, not container startup or HTTP acceptance. Correlate retries separately.
- Parse `Log_s` in `ContainerAppConsoleLogs_CL`, filter the intended environment/app/container, and deduplicate by execution/attempt/event. Create separate success and failure queries returning terminal executions, and an overdue query anti-joining starts against either terminal outcome after maximum runtime plus ingestion grace. Each rule fires when returned row count is greater than zero.
- A crash, OOM, or forced termination may emit no terminal event: classify an overdue start as **unknown/missing result**, not confirmed failure. A crash before `started`, or lost logs, is invisible to this query; compare an independently recorded expected execution/schedule with observed events. Container Apps system logs provide supporting diagnostics, not proof of business success. Arbitrary unscheduled executions without any independent record cannot be detected.
- Initially use stateful rules grouped by stable workload, not unique run IDs. Action groups notify on firing and supported resolution transitions; resolution means the query condition cleared, **not** that an execution succeeded. Frequent runs can keep a rule fired and suppress subsequent notifications. Stateless rules can repeatedly notify for the same events in overlapping windows. Deduplication inside KQL does not deduplicate deliveries; neither mode guarantees one notification per execution.

## 2. Repository-specific implementation steps

1. Obtain the Go source and deployment definitions; identify `main`, the true work boundary, error/exit/panic paths, and existing logging before selecting files to change. Confirm Container App versus Container Apps Job, concurrency, retries, and scheduling.
2. Instrument that boundary using the existing logger or Go standard library; report handled failures before nonzero exit and flush buffered output. Handle shutdown best-effort without claiming recovery from SIGKILL/OOM.
3. Add reviewed KQL and infrastructure definitions in the project's agreed format, including expected-run detection where required. Keep IDs available for investigation rather than high-cardinality alert dimensions.
4. Once implementation is approved, test success, errors, panic/shutdown, missing completion/start, overlapping runs, retries, duplicate and late logs. Validate queries against the deployed schema, then test action-group delivery and repeated-run behavior. There is no existing test/build infrastructure to run now; this change creates only this plan.

## 3. Required Azure configuration and unresolved decisions

- Configure the Container Apps environment's Log Analytics destination and workspace to retain console/system logs. If using the Azure Monitor destination instead, configure environment diagnostic settings routing those categories to the workspace. Verify actual table/column names and avoid duplicate collection.
- Provision three workspace-scoped scheduled query rules and an action group with confirmed recipients/common alert schema. Proposed starting evaluation frequency: five minutes; choose lookback, runtime deadline, and ingestion grace after measuring real timings. Lookback must cover starts through completion/deadline plus grace; scheduled log-alert queries scan at most two days. Longer runs require a revised durable pending-execution signal design. Configure retention, severities, RBAC for deployment/query access, budgets, and any suppression rules; the application needs no alert-management permissions.
- Expect several minutes of ingestion delay plus evaluation and notification delivery time, not real-time delivery. Late/lost logs can cause missed or false missing-result alerts. Action-group rate limits and suppression can further affect delivery.
- Decide whether aggregated operational notifications suffice or every execution requires a notification; confirm recipients/channels, retry-versus-final-result semantics, schedules/expected-run source, maximum runtime, latency target, and acceptable duplicates/cost. Unique execution dimensions increase cardinality/cost and do not establish exactly-once delivery.
- Built-in emails provide alert context and query links, not arbitrary execution reports/attachments. Current log-alert rules support static/dynamic custom email subjects; custom properties do not turn the email body into a report template. If bespoke bodies or guaranteed per-run delivery are mandatory, explain these limits and revisit the design before proposing a Logic App or separate delivery component.
